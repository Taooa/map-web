# Coordinate Toolkit V1 开发路线图

> 产品：PeachTools Coordinate Toolkit  
> 版本：V1  
> 状态：执行基线  
> 策略：产品闭环优先  
> 更新日期：2026-07-29

## 0. 文档目的

本文调整 Coordinate Toolkit V1 的开发顺序：从“先完成完整架构体系，再接入产品功能”，调整为“先打通用户可验证的产品闭环，再依据实际复杂度补齐架构”。

调整不改变产品定位、V1 功能边界和已有正确领域约束，也不否定现有架构文档。被降级的设计作为后续扩展方案保留，但不再作为 V1 功能开发的前置条件。

V1 实施原则：

1. 每个阶段都交付用户可见、可操作、可测试的增量；
2. 先解决当前四种坐标体系和三个地图平台的确定需求；
3. 只为已经出现的复杂度建立抽象；
4. 复用 `map-tools` 已验证的业务能力，不重新发明算法；
5. 不复制参考项目页面、状态管理和项目结构；
6. 不为了满足架构形式延迟核心闭环。

## 1. 当前状态总结

### 1.1 已完成

- React、TypeScript、Vite、pnpm 工程骨架；
- `/`、`/points`、`/map/amap`、`/map/baidu`、`/map/tianditu` 路由；
- PeachTools Design Token 和基础视觉规范；
- 首页、Point Manager、三个地图页面原型；
- Point 列表 Mock 数据；
- 搜索、选择、详情抽屉和配置弹窗等 Mock 交互；
- Point、Coordinate、CoordinateSystem、Source 等 Domain 类型；
- `original` 与 `converted` 分离的数据约束；
- PointRepository 等存储接口；
- Coordinate Core 的部分扩展性契约；
- 基础构建、Lint、Vitest 和页面测试。

### 1.2 当前缺口

当前页面能够表达产品形态，但尚未形成真实业务闭环：

- 新增点位不会形成真实 Point；
- 点位列表仍由 Mock 数据驱动；
- 坐标转换按钮不执行算法；
- 文件导入没有解析和字段映射；
- 地图页面不加载 SDK，也不展示真实 Marker；
- 数据刷新后不能恢复；
- API Key、AK、Token 不会保存。

### 1.3 路线调整原因

现有架构设计覆盖了坐标图、算法注册、多个 Repository、分层错误和 Use Case 等长期扩展问题，但 V1 当前最需要验证的是：

- 用户能否顺利输入和管理点位；
- 已有坐标算法能否在新数据模型下正确工作；
- 点位能否在三个真实地图平台上完成验证；
- 文件导入流程是否易用；
- 浏览器本地工具是否能稳定完成整条流程。

因此，V1 不再以完整实现所有架构契约作为阶段验收条件，而以核心流程是否真实可用作为首要标准。

## 2. V1 目标

### 2.1 产品目标

交付一个运行在浏览器中的设备点位坐标转换与地图验证工作台，让用户能够完成：

```text
点位输入
    ↓
点位列表
    ↓
坐标转换
    ↓
地图验证
```

### 2.2 最小成功场景

1. 用户在 Point Manager 手动添加一个 WGS84 点位；
2. 点位立即出现在列表中；
3. 用户将该点位转换为 GCJ02 或 BD09；
4. 原始坐标不变，转换结果显示在详情中；
5. 用户打开对应地图页面；
6. 地图使用正确的平台坐标展示 Marker；
7. 用户点击 Marker 查看点位名称和坐标。

当以上流程在高德、百度和天地图的适用坐标契约下可以稳定完成时，V1 核心闭环成立。

### 2.3 V1 范围

V1 保持既定产品范围：

- 手动添加点位；
- Excel、CSV、JSON 文件与 JSON 粘贴导入；
- 字段映射和导入坐标系选择；
- 点位列表、搜索、详情、编辑和删除；
- WGS84、GCJ02、BD09、上海2000；
- 单个和批量坐标转换；
- 高德、百度、天地图独立验证；
- API Key、AK、Token 配置；
- 浏览器本地持久化。

V1 仍不包含：

- 自动识别坐标系；
- 点位异常判断和区域校验；
- GeoJSON；
- 用户系统和后端；
- 通用 Geometry、Layer 或插件框架；
- CGCS2000 普通用户入口。

## 3. 保留架构

以下设计直接保护数据正确性或产品边界，应继续作为 V1 实现约束。

### 3.1 Point 模型

保留统一 Point 作为产品核心对象。

最低必要字段：

- `id`；
- `name`；
- `source`；
- `coordinates`；
- `createdAt`；
- `updatedAt`。

Point 不保存原始文件行、地图 Marker、页面选择状态和无关业务字段。

### 3.2 `original` / `converted`

保留原始坐标和转换缓存分离：

- `original` 始终存在；
- 转换操作不得覆盖 `original`；
- `converted` 按目标坐标系保存；
- 修改原始坐标后清除已有转换缓存；
- 只修改名称时保留转换缓存；
- 转换失败不得写入伪坐标。

这是 V1 不可降级的数据不变量。

### 3.3 PointRepository

保留一个 PointRepository 边界，页面不直接管理全局点位集合，也不直接绑定具体持久化技术。

V1 接口只需要支持实际使用的方法：

- `get`；
- `list`；
- `create`；
- `update`；
- `delete`。

批量操作可以先由 Feature 调用基础方法完成；只有出现明确的性能或事务需要时，再扩充专用批量接口。

### 3.4 CoordinateService 入口

V1 将坐标转换统一收敛到一个简单的 `CoordinateService` 入口：

```text
transform(coordinate, targetSystem)
```

该入口负责：

- 校验源和目标坐标体系；
- 调用已验证转换逻辑；
- 返回成功结果或明确失败；
- 提供算法版本标识；
- 禁止使用 `(0, 0)` 等伪结果表示错误。

页面和 Point Feature 不直接调用 `gcoord`、`proj4` 或旧项目函数。

### 3.5 三地图页面隔离

继续保留三个独立路由：

- `/map/amap`；
- `/map/baidu`；
- `/map/tianditu`。

原因：

- SDK、凭据和全局对象不同；
- 平台坐标契约不同；
- 生命周期和错误状态需要独立处理；
- 单个平台故障不应影响其他平台。

V1 可以共享页面壳和少量地图公共接口，但不以建设完整通用 GIS 框架为目标。

## 4. 降级设计

“暂停”表示不作为 V1 当前阶段的实现前置条件，而不是删除已有文件或否定长期价值。已有契约可保留，但生产流程暂不围绕它们继续扩建。

### 4.1 TransformationGraph

#### 暂停内容

- 通用图搜索；
- 路径权重和精度等级比较；
- 动态增加任意坐标节点；
- 路径签名体系。

#### V1 降级实现

使用明确、可审计的有限转换表，覆盖正式启用的转换路径：

```text
WGS84 ↔ GCJ02
GCJ02 ↔ BD09
WGS84 → GCJ02 → BD09
BD09 → GCJ02 → WGS84
上海2000相关路径：验证通过后启用
```

路径表只能存在于 CoordinateService 内部，不能散落在页面中。若未来增加更多坐标系或出现多条可选路径，再恢复 TransformationGraph。

### 4.2 AlgorithmRegistry

#### 暂停内容

- 运行时动态注册；
- 插件式算法加载；
- 多算法候选选择；
- 通用能力元数据。

#### V1 降级实现

由 CoordinateService 静态组合少量已验证算法函数。每个算法仍保留：

- 稳定名称；
- 版本；
- 来源说明；
- 固定样本测试；
- 源和目标坐标系。

当同一转换出现多个实现、需要运行时替换，或正式增加更多坐标体系时，再恢复 Registry。

### 4.3 多层 Error

#### 暂停内容

- Domain、Core、Adapter、Feature 各自建立大型错误类层级；
- 为每个失败原因建立继承类；
- 页面逐层翻译错误对象。

#### V1 降级实现

每个模块返回小型可判别结果：

```text
{ ok: true, value }
{ ok: false, code, message? }
```

优先保留用户需要采取不同措施的错误码，例如：

- `INVALID_INPUT`；
- `UNSUPPORTED_TRANSFORMATION`；
- `TRANSFORMATION_FAILED`；
- `STORAGE_FAILED`；
- `SDK_LOAD_FAILED`；
- `MISSING_CREDENTIAL`。

日志细节与用户文案分离，不返回敏感凭据或完整原始文件内容。

### 4.4 ImportRepository

#### 暂停内容

- 导入记录独立查询功能；
- 导入历史页面；
- 导入批次撤销；
- 导入记录复杂索引。

#### V1 降级实现

Phase 3 首先将解析成功的标准 Point 交给 PointRepository 保存。导入过程只在当前会话显示：

- 文件名；
- 字段映射；
- 总行数；
- 成功数；
- 跳过数和失败原因。

Phase 5 根据真实追溯需求决定是否保存最小 ImportRecord。不得保存原始文件或完整原始行。

### 4.5 SettingsRepository

#### 暂停内容

- 通用设置 Store；
- 设置 schema migration；
- 设置 Repository 抽象；
- 尚未出现的主题和展示偏好。

#### V1 降级实现

只为真实存在的小型设置提供简单存储模块：

- 高德 Key；
- 百度 AK；
- 天地图 Token；
- 必要时保存表格页大小。

地图凭据与普通设置分离，不进入 URL、日志和 Point 数据。

### 4.6 Use Case 类体系

#### 暂停内容

- 每个操作一个类；
- Command/Handler；
- DI 容器；
- 空泛的应用服务层。

#### V1 降级实现

按 Feature 提供小型函数或 Hook：

- `createPoint`；
- `updatePoint`；
- `deletePoint`；
- `transformPoint`；
- `transformPoints`；
- `importPoints`。

函数负责真实流程编排，页面只调用 Feature 的公开入口。只有当流程出现复用、复杂事务或多入口协调时，才提取独立 Use Case。

## 5. 开发阶段

实施顺序：

```text
Phase 1 真实 Point 数据
          ↓
Phase 2 坐标转换
          ↓
Phase 3 文件导入
          ↓
Phase 4 地图 SDK
          ↓
Phase 5 优化和持久化
```

阶段之间允许进行少量 UI 准备，但后一阶段不得阻塞前一阶段闭环验收。

## 5.1 Phase 1：真实 Point 数据

### 目标

用真实内存数据替换 Point Manager 的 Mock 数据，完成手动点位管理。

### 实现内容

- 实现最小 Point Feature；
- 实现内存版 PointRepository；
- 新增点位表单；
- 支持 WGS84、GCJ02、BD09、上海2000的输入类型；
- 经纬度使用 `lng/lat`，投影坐标使用 `x/y`；
- 点位列表读取真实 Repository 数据；
- 名称搜索；
- 点位详情；
- 编辑和删除；
- 单选、全选当前结果及批量删除；
- 页面明确提示当前为内存模式，刷新会丢失。

### 本阶段不做

- 坐标算法；
- 文件上传；
- 地图 SDK；
- IndexedDB。

## 5.2 Phase 2：坐标转换

### 目标

完成“选择点位 → 选择目标坐标系 → 转换 → 更新列表”的真实流程。

### 实现内容

- 建立简单 CoordinateService；
- 审计并迁移 `map-tools` 已验证的 WGS84、GCJ02、BD09逻辑；
- 建立固定转换路径表；
- 单个转换；
- 批量转换；
- 将成功结果写入 `converted`；
- 缓存命中时不重复计算；
- 修改 original 后清除转换缓存；
- 显示成功、失败和跳过数量；
- 固定样本和往返误差测试。

### 上海2000门槛

启用前必须确认：

- 参数来源；
- 投影定义或 EPSG 信息；
- X/Y 轴顺序；
- 单位；
- 权威测试样本；
- 可接受精度。

验证未完成时保留 UI 状态说明，但不得产生未经确认的正式转换结果。

## 5.3 Phase 3：文件导入

### 目标

让用户能从真实文件或 JSON 文本创建 Point。

### 实现内容

- Excel Parser；
- CSV Parser；
- JSON 文件 Parser；
- JSON 粘贴；
- 数据预览；
- 名称、经度/X、纬度/Y字段映射；
- 整批数据选择一个坐标系；
- 标准化为 Point；
- 成功和跳过统计；
- 批量写入 PointRepository；
- 文件大小和预览行数限制；
- 不保存原始文件内容和无关业务字段。

字段自动匹配只能作为下拉框预填建议，用户必须确认；不得自动识别坐标系。

## 5.4 Phase 4：地图 SDK

### 目标

使用真实地图完成点位位置验证。

### 实现内容

- 高德、百度、天地图凭据配置；
- 无凭据时不加载 SDK；
- 三个平台各自的 SDK Loader；
- 地图初始化与销毁；
- 点位选择；
- 使用正确平台坐标展示 Marker；
- InfoWindow；
- `fitView` 或平台等价能力；
- 加载中、加载失败、无凭据和无点位状态；
- Key 变化后的重新加载策略；
- 页面切换后的实例、事件和覆盖物清理。

### 最小地图边界

页面不直接散落调用 SDK。每个平台只需提供 V1 使用的最小接口：

- `initialize`；
- `setMarkers`；
- `openInfoWindow`；
- `fitView`；
- `destroy`。

底图切换、测量、绘制、通用 Layer 和插件机制不是本阶段前置条件。

## 5.5 Phase 5：优化和持久化

### 目标

在核心流程验证完成后，使数据可恢复，并解决真实使用中暴露的性能和体验问题。

### 实现内容

- Point 的 IndexedDB 实现；
- 应用启动时恢复 Point；
- PointRepository 内存实现切换为持久化实现；
- 地图凭据本地保存；
- schema version 和最小升级策略；
- 存储失败和配额不足提示；
- 列表分页或必要时虚拟化；
- Marker 数量基线与必要聚合；
- 文件解析性能优化；
- 导入记录是否持久化的产品决策；
- 桌面 Chrome、Edge 回归；
- 键盘、焦点与响应式检查。

持久化放在闭环之后，不表示不重要，而是先用内存实现确认模型、编辑规则和转换缓存行为，避免过早固化错误 schema。

## 6. 每阶段验收标准

## 6.1 Phase 1 验收

用户可以在 `/points`：

1. 手动新增 geographic Point；
2. 手动新增 projected Point；
3. 在列表中看到真实新增结果；
4. 搜索、查看详情和编辑名称；
5. 编辑原始坐标；
6. 单个或批量删除；
7. 完成单选和全选当前结果。

数据规则：

- geographic 与 projected 不混用字段；
- Point 不包含原始文件行和页面状态；
- `original` 始终存在；
- Mock Point 不再是页面生产数据源；
- 刷新丢失有明确提示。

质量门槛：

- 构建、类型检查、Lint 和测试通过；
- Point CRUD 与页面主流程有自动化测试。

## 6.2 Phase 2 验收

用户可以：

1. 选择一个或多个 Point；
2. 选择目标坐标系；
3. 完成 WGS84、GCJ02、BD09之间的有效转换；
4. 在列表和详情中看到 `converted`；
5. 对已有目标坐标使用缓存；
6. 看到批量成功与失败统计。

正确性门槛：

- 原始坐标不被覆盖；
- 无效输入不产生转换结果；
- 失败不使用 `(0, 0)`；
- 固定基线样本在规定容差内通过；
- 算法有来源和版本；
- 上海2000未验证前不可静默启用；
- CGCS2000不出现在普通入口。

## 6.3 Phase 3 验收

用户可以：

1. 选择 Excel、CSV 或 JSON 文件；
2. 粘贴 JSON 对象数组；
3. 看到字段和有限行预览；
4. 手动确认名称、X、Y映射；
5. 为整个批次选择一个坐标系；
6. 确认后在 Point Manager 看到导入结果；
7. 看到成功、跳过和失败统计。

数据门槛：

- 不自动识别坐标系；
- 不保存无关业务字段；
- 不保存原始文件内容；
- 无效行不会阻止其他有效行导入；
- 字段映射和解析错误有明确提示；
- Parser 和导入流程有样本测试。

## 6.4 Phase 4 验收

三个地图页面分别满足：

1. 无凭据时不加载 SDK；
2. 用户可以配置当前平台凭据；
3. SDK 可以成功初始化；
4. 用户可以搜索和选择 Point；
5. 平台所需坐标不存在时按需转换；
6. Marker 数量和已选点位一致；
7. 点击 Marker 能看到名称和坐标；
8. 多点可以适配视野；
9. 离开页面后地图实例和事件正确销毁；
10. 一个地图平台失败不影响其他页面。

平台门槛：

- 高德使用 GCJ02；
- 百度使用 BD09；
- 天地图坐标契约在接入前形成明确结论；
- Key、AK、Token 不进入源码、URL或日志；
- 地图 SDK 请求第三方平台的边界有用户说明。

## 6.5 Phase 5 验收

持久化：

- 刷新后 Point 和转换缓存可以恢复；
- 删除的数据刷新后不再出现；
- 升级 schema 不覆盖 original；
- 凭据可保存和清除；
- 存储不可用时给出可执行提示。

性能与体验：

- 约定规模的点位列表操作流畅；
- 地图达到 Marker 基线后采用已验证的聚合或降载策略；
- 大文件不会导致无限制预览；
- 三个地图页面状态和操作结构一致；
- 当前桌面 Chrome、Edge 核心流程通过；
- 所有核心流程可通过键盘完成。

发布门槛：

```text
pnpm build
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test:run
```

命令全部通过，并完成一次以下真实回归：

```text
手动新增
→ 文件导入
→ 点位选择
→ 批量转换
→ 高德验证
→ 百度验证
→ 天地图验证
```

## 7. 路线治理

### 7.1 何时恢复被暂停设计

只有出现实际信号时才恢复更复杂抽象：

| 设计 | 恢复信号 |
| --- | --- |
| TransformationGraph | 新增多个坐标系、同一目标存在多条路径或需要动态寻路 |
| AlgorithmRegistry | 同一转换存在多个实现、需要运行时替换或第三方扩展 |
| 多层 Error | 不同层出现稳定且需要独立处理的错误语义 |
| ImportRepository | 用户需要导入历史、追溯、批次撤销或审计 |
| SettingsRepository | 设置数量增加、需要迁移或多模块共同访问 |
| Use Case 类体系 | 同一业务流程被多个入口复用，或事务编排明显复杂 |

### 7.2 文档关系

- PRD V2 继续定义产品范围；
- ARCHITECTURE 和 ADR 继续作为长期架构方向；
- 本路线图覆盖 V1 的实施顺序和最小实现策略；
- 若本路线图与旧 Phase 计划在“是否作为 V1 前置条件”上冲突，以本路线图为准；
- 若涉及坐标正确性、原始坐标保护、凭据安全和地图生命周期，仍遵守已有 ADR 的安全与数据约束。

### 7.3 V1 完成定义

V1 完成不是“所有预设计架构都已实现”，而是：

- 核心闭环真实可用；
- 数据模型和转换结果正确；
- 三个地图平台可以独立验证；
- 数据能够在浏览器本地恢复；
- 失败状态诚实且可处理；
- 测试覆盖关键规则；
- 代码结构足以支持下一次需求变化，同时没有为未知需求承担过高复杂度。
