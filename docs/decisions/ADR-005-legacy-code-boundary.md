# ADR-005：旧代码迁移边界

- 状态：已接受
- 日期：2026-07-28
- 决策范围：Coordinate Toolkit V2 Phase 0 及后续迁移工作
- 关联文档：ADR-001、MIGRATION-MATRIX、ARCHITECTURE、TASKS V2

## 背景

Coordinate Toolkit V2 不是从零开发。`reference/map-tools` 已包含坐标转换、文件解析、点位处理和三类地图 SDK 使用经验；`reference/gisviewer-react` 包含配置驱动、平台实现选择、组件容器和生命周期管理经验。

旧项目同时存在以下问题：

- 页面直接编排解析、转换、地图和导出，页面耦合较重；
- React Hook、地图 SDK 对象和业务状态相互耦合；
- UI、文案和样式不符合 PeachTools Design System；
- 领域模型、Adapter、Repository 等边界不足；
- 部分能力只有入口或占位实现，不能等同于可迁移的成熟功能；
- 旧代码存在乱码、`any`、隐式全局对象和隐藏环境依赖。

因此，既不能把旧项目当成废弃物全部重写，也不能直接复制其工程和页面。

## 决策

采用“能力迁移，而不是项目代码迁移”：

```text
reference 项目
    ↓ 分析
能力、行为、参数、测试样例和风险
    ↓ 提取
迁移分类与可验证契约
    ↓ 实现
V2 新架构中的 Domain / Core / Adapter / Feature
```

允许：

- 阅读和分析 `reference/`；
- 提取算法、纯工具函数、输入输出行为和测试样例；
- 在来源、依赖和验证条件明确时，迁入成熟的纯逻辑实现；
- 用旧项目的可观察行为建立基线测试；
- 参考 `gisviewer-react` 的配置驱动和生命周期思想；
- 在 V2 接口下封装经审计的旧逻辑。

禁止：

- 整体复制旧 `src/`；
- 复制旧页面或路由结构；
- 复制旧 CSS、Tailwind 页面样式或图片资产作为新 UI；
- 复制旧状态管理和页面内编排方式；
- 让 V2 页面直接依赖 reference 文件；
- 修改 `reference/map-tools` 或 `reference/gisviewer-react`；
- 因旧代码存在某个按钮、类型或空函数，就宣称能力已经可用；
- 未验证即沿用旧地图 Key、环境变量、投影参数或平台坐标假设。

迁入 V2 的实现必须成为新项目自身受测试、受版本控制的代码；运行时不得从 `reference/` 引用。

## 迁移分类

### M1：直接迁移封装

适用于业务逻辑成熟、边界较纯、依赖清晰且能以测试确认行为的实现。

典型对象：

- WGS84、GCJ02、BD09 的成熟转换调用；
- 经审计的纯工具函数；
- 不依赖页面和 SDK 生命周期的确定性逻辑。

处理方式：

1. 保留经过验证的核心实现或算法库调用；
2. 移除 React、页面状态和旧类型依赖；
3. 接入 V2 接口、错误类型和算法版本；
4. 使用基线样本和新单元测试锁定行为；
5. 记录来源文件和第三方许可证。

M1 不代表无条件复制。不能证明等价性时降为 M2。

### M2：保留行为重构

适用于用户行为或业务结果基本正确，但模块边界、错误处理或生命周期需要调整的能力。

典型对象：

- 地图 SDK 加载；
- Marker 和 InfoWindow 管理；
- Excel、JSON 文件解析；
- 字段映射建议；
- 上海2000已有转换基础；
- 三平台有限底图切换。

处理方式：

1. 先描述旧行为和已知缺陷；
2. 定义新 Port、Adapter 或 Core 契约；
3. 在新模块中实现，不保留旧页面编排；
4. 只保证经确认的产品行为，不保证旧内部结构；
5. 补齐失败、取消、销毁、重复调用和边界测试。

### M3：重新实现

适用于旧实现不满足 V2 正确性、数据边界或产品要求的能力。

典型对象：

- V2 Point、Coordinate、Source 数据模型；
- IndexedDB 与 Repository；
- Point Manager；
- JSON 粘贴和统一导入状态机；
- 标准 CSV 解析；
- PeachTools UI。

处理方式：

1. 以 PRD、ADR 和 Architecture 为唯一目标契约；
2. 旧实现只提供场景和失败经验；
3. 新实现不得继承旧页面状态或数据结构；
4. 新增完整测试和验收样例。

### M4：不迁移

适用于不符合 V1 产品方向、只是 Demo、质量不可接受或会扩大产品边界的内容。

典型对象：

- 旧页面布局和旧样式；
- 自动识别坐标系；
- GeoJSON 分支；
- 绘制、测量等 V1 非核心工具；
- 搜索、天气和临时 Demo 代码。

处理方式：

- 不进入 V1 代码和导航；
- 可在迁移矩阵中保留事实记录；
- 后续只有经过新 PRD/ADR 决策后才能重新进入范围。

## 分类规则

对每项能力按以下顺序判断：

1. 是否属于 V1？否，则 M4。
2. 旧项目是否存在真实实现，而非类型、按钮或空函数？否，则 M3 或 M4。
3. 是否是与 React、页面、SDK 无关的成熟纯逻辑？是，且有可验证样本，则 M1。
4. 用户行为是否值得保留，但边界需要重建？是，则 M2。
5. 正确性或数据模型是否不满足 V2？是，则 M3。

分类可以在审计后变更，但必须更新迁移矩阵、原因和评审记录。M1 升级为正式可迁移前必须有基线测试；验证失败时降级为 M2 或 M3。

## 迁移原则

1. **先证明再迁移**：存在代码不等于能力已验证。
2. **行为优先于结构**：保留正确结果，不保留不合适的组织方式。
3. **领域与平台隔离**：坐标算法不依赖 React；地图能力不泄漏 SDK 类型。
4. **缺陷不兼容**：CSV `split`、无效数值变 `0`、空工具函数等不作为兼容行为。
5. **参数可追溯**：投影参数、地图坐标契约和 SDK 版本必须有来源。
6. **小步迁移**：每项能力独立进入、测试和回退，不做一次性大搬迁。
7. **reference 只读**：不通过修改旧项目来“方便迁移”。
8. **避免过度抽象**：只为 V1 已确认的平台和能力建立最小接口。

## 风险

| 风险 | 表现 | 控制措施 |
|-|-|-|
| 隐藏依赖 | 逻辑依赖 Hook、环境变量、全局 SDK 或页面状态 | 迁移前列出依赖，使用 Port 隔离 |
| 错误成熟度判断 | 有代码但无可靠样本或实现为空 | 以基线测试和人工样本验收为准 |
| 算法漂移 | 重构改变坐标结果 | 固定样本、容差、算法版本和来源 |
| SDK 行为漂移 | 平台升级导致加载或销毁失效 | Loader 状态机、Adapter 契约、真实 Key 验证 |
| 许可证风险 | 迁入代码或依赖来源不清 | Phase 1 前完成许可证清单 |
| 迁移层永久化 | `legacy` 成为长期业务入口 | 设删除门槛，Feature 禁止直接依赖 legacy |
| 范围回流 | Demo 工具进入 V1 | 以 PRD V2 和 M4 清单做验收 |

## 验收标准

一项迁移只有同时满足以下条件才算完成：

- 在 `MIGRATION-MATRIX.md` 中有来源、旧位置、等级和处理方式；
- V2 代码运行时不依赖 `reference/`；
- 新模块位于 Architecture 规定的层，依赖方向合规；
- M1/M2 有覆盖正常、边界和失败路径的基线或回归测试；
- 坐标能力记录算法/参数版本、样本来源和容差；
- 地图能力通过重复初始化、切页、清空 Marker 和销毁验收；
- 旧缺陷没有被当成兼容行为迁入；
- PeachTools UI 不复用旧页面或旧 CSS；
- 迁移完成后能删除对应临时 legacy 适配而不影响 Feature；
- 代码评审能够从需求追踪到迁移矩阵、实现和测试。

## 影响

正面影响：

- 保住成熟业务经验，减少无意义重写；
- 新项目边界不受旧工程结构约束；
- 每项迁移都有证据、风险和退出条件。

代价：

- Phase 0 需要额外建立样本、基线和迁移清单；
- M2 能力会产生短期对照成本；
- 上海2000和地图 SDK 等能力在验证完成前不能按“已完成”计入。
