# Coordinate Toolkit V2 Phase 0 迁移基线报告

## 0. 结论

参考项目具备可利用的坐标转换、文件读取、三地图 Marker/InfoWindow 和生命周期经验，但“仓库中存在实现”不等于“生产基线已经确认”。当前可以有条件进入 Phase 1 的工程初始化与领域接口设计；不能把上海2000、CGCS2000/天地图坐标契约、三地图真实 Key 验证和大量点性能视为已完成。

本次为静态分析，不安装依赖、不运行参考项目或测试、不修改 reference。

# 1. 已确认能力

“已确认”指静态代码中能定位真实实现和调用链，不代表已完成 V2 精度或生产验收。

## 1.1 map-tools

| 能力 | 代码证据 | 基线结论 |
|-|-|-|
| WGS84/GCJ02/BD09转换 | `useCoordTransform.ts` 使用 gcoord，`coordParams.ts` 定义路径 | 存在单点、批量、全目标和地图目标转换行为；适合建立 M1 基线 |
| 上海2000基础 | `useCoordTransform.ts` 注册 proj4 定义及正反转换 | 已有实现基础，不是“无法实现”；参数和精度尚未被本报告确认 |
| CGCS2000线索 | 类型、投影定义、路径和天地图目标映射 | 旧实现存在，但部分将其近似映射到 WGS84，不能直接正式启用 |
| Excel读取 | `file.ts` 使用 SheetJS 读取首个工作表 | 基本流程存在；缺少工作表选择和完整错误边界 |
| CSV读取 | `file.ts` 读取文本并按逗号拆分 | 入口存在，但解析实现不符合标准 CSV，不能作为可复用实现 |
| JSON文件 | `file.ts` 支持数组及 `features[].properties` | 数组读取行为可参考；GeoJSON分支不属于 V1 |
| 字段匹配 | `mapUtils.ts` 与对应测试文件 | 存在经纬度/X/Y/名称字段建议逻辑；V2仍要求用户确认 |
| 手动点位与批量文件流程 | `PointInput.tsx`、`CoordConvert.tsx`、`MapVisual.tsx` | 用户流程可参考；数据只在页面状态中，模型需重建 |
| 高德地图 | `useAmap.ts` | 有 SDK加载、Marker、InfoWindow、底图、部分绘制/测量以及多点策略 |
| 百度地图 | `useBmap.ts` | 有 SDK加载、Marker、InfoWindow和基础底图行为；工具能力不完整 |
| 天地图 | `useTianditu.ts` | 有 SDK加载、Marker、InfoWindow和底图行为；坐标契约待验证 |
| 清理行为 | 三个地图 Hook 的 `destroy` | 存在销毁意图；全局回调、script和事件清理仍需重新设计 |
| 基础测试资产 | `coordParams.test.ts`、`file.test.ts`、`mapUtils.test.ts` | 有部分工具测试文件；本次未执行，且未看到足够的坐标精度金样本 |

## 1.2 gisviewer-react

| 能力 | 代码证据 | 基线结论 |
|-|-|-|
| 平台实现选择 | `MapContainer.tsx` 选择 ArcGIS2D/ArcGIS3D/Mapbox 实现 | 可参考 Provider/Adapter 的装配思想 |

# 2. 待验证能力

## 2.1 上海2000

当前代码包含如下基础参数：横轴墨卡托/高斯类投影描述、中央经线、假东/北、GRS80 椭球以及 CGCS2000 正反转换。

开发前必须确认：

- 参数的权威来源、适用区域和版本；
- 正式 EPSG 代码，或明确记录为业务自定义 CRS；
- WKT/proj4 定义是否完整且语义一致；
- 输入/输出 X、Y 轴顺序及旧数据是否存在反序；
- 米、度等单位和小数精度；
- 至少一组来自业务/测绘来源的正向与反向测试样本；
- 可接受的平面和经纬度误差标准；
- 超出适用范围时的错误策略；
- 参数修订时算法版本与转换缓存的失效方式。

门槛：以上内容形成验证记录并由业务/GIS责任人签字前，不得在生产入口静默生成“正式上海2000结果”。

## 2.2 CGCS2000

必须确认：

- 用户是否实际导入 CGCS2000 经纬度或投影数据；
- CGCS2000在 V1 是内部转换节点、天地图契约，还是用户坐标入口；
- 数据采集年份、精度和基准转换需求；
- 业务允许把 WGS84 与 CGCS2000近似处理的场景、范围与误差；
- 是否需要独立算法边、独立缓存键和展示标签；
- 若仅服务天地图，是否应隐藏在 Provider 配置内部。

当前结论：保留扩展节点，默认不开放用户入口。

## 2.3 地图SDK

三个平台分别确认：

- Key/AK/Token申请方式、授权人和轮换流程；
- 开发与生产域名白名单、HTTPS和 Referer 限制；
- SDK版本、加载 URL、插件列表及官方推荐加载方式；
- 同页面重复加载、并发加载和 Key 变更行为；
- 缺少 Key、Key无效、超时、限额和网络失败时的产品提示；
- 初始化、切换页面、Marker更新、InfoWindow关闭和 destroy；
- SDK全局对象、callback、script和事件监听的清理边界；
- 三平台 fitView 等价行为和最大缩放级别。

特别地，天地图需单独确认传入坐标是 WGS84、CGCS2000或某个可接受近似契约。

## 2.4 文件与字段

- Excel工作表选择、合并单元格、公式和日期处理；
- CSV编码、BOM、引号、嵌入换行和大文件；
- JSON顶层对象数组、空数组、混合字段和无效数字；
- 字段映射建议的中英文别名；
- 投影坐标应显示 X/Y，不能沿用 lng/lat 语义；
- 错误行跳过、整批阻止或部分保存的最终产品策略。

## 2.5 点位与存储

- Point编辑是否进入 V1；
- 删除导入记录时是否级联删除点位；
- 重复导入/同名点位是否去重；
- IndexedDB目标容量、配额不足和隐私模式行为；
- schema版本、导出/备份和清空数据策略。

## 2.6 性能

- Point Manager可接受的点数和响应时间；
- 普通 Marker、聚合、海量点的设备基线和阈值；
- 三平台在同一数据集上的能力差异和降级策略；
- 转换/解析是否需要 Worker；
- 页面切换后内存、监听器和 SDK 实例是否回落。

# 3. 重构风险

## 3.1 旧逻辑隐藏依赖

**问题：** 坐标转换位于 React Hook，地图 Hook依赖环境变量、window全局 SDK、页面 Point 结构和HTML字符串。

**影响：** 整体搬迁会让 Core依赖React，让 Adapter泄漏旧模型，也可能把密钥和页面状态带入新架构。

**建议：** 先定义纯 Port；逐项列出输入、输出、依赖和错误；M1仅迁入纯算法调用，M2重新实现装配。

## 3.2 坐标精度和错误传播

**问题：** 旧代码部分把 CGCS2000按WGS84映射，并将某些无效解析结果变成 `0`。

**影响：** 地图可以正常显示但位置错误，属于最难发现的静默错误。

**建议：** 使用带 kind/unit/crs 的 Coordinate；禁止错误值回退为0；建立金样本、容差、算法版本和缓存失效。

## 3.3 SDK生命周期

**问题：** Loader缓存 Promise，却未完整标识/清理 script与全局callback；页面同时实例化三个Hook再选择当前Hook。

**影响：** 切页、失败重试或Key变化可能产生重复 SDK、幽灵事件和内存泄漏。

**建议：** 一个页面只装配一个 Provider；Loader采用状态机；MapCore拥有唯一 Adapter并保证 destroy幂等。

## 3.4 大量Marker性能

**问题：** 高德存在多套渲染策略，但阈值未经目标设备验证；批量渲染调用 `addMarkers` 时可能反复清空；百度和天地图缺少等价策略。

**影响：** 大文件导入后卡顿、只显示最后一批、内存激增，且三平台体验不一致。

**建议：** 先定义数据规模档位和基线设备；按 Capability选择策略；批量API区分 replace/append；做内存和切页测试。

## 3.5 浏览器存储限制

**问题：** 参考项目未提供 IndexedDB基线；浏览器配额、无痕模式、事务中断和schema升级均未验证。

**影响：** 用户认为已保存，但刷新后数据缺失，或升级后无法读取。

**建议：** Repository统一错误；导入和点位写入使用事务；提供配额/不可用提示、schema迁移测试和数据导出兜底。

## 3.6 参考架构过度迁移

**问题：** `gisviewer-react` 包含ArcGIS/Mapbox、图层、Geometry、Widget、热力图和三维能力。

**影响：** V2可能被扩建为GIS框架，拖慢核心工作台。

**建议：** 只参考配置、Provider选择和生命周期；不迁移其平台实现、Widget系统和通用GIS模型。

# 4. 开发前建议

## 4.1 Phase 1开始前必须完成

以下是启动项目初始化的硬门槛：

1. 评审并接受 ADR-005；
2. 审核 `MIGRATION-MATRIX.md` 的44项分类，指定负责人；
3. 确认 V1 是否包含“点位编辑”，并统一文档口径；
4. 确认 settings 在 IndexedDB/localStorage 的数据归属及命名；
5. 明确 PeachTools Design System 的包、版本、Token和Tailwind接入方式；
6. 确定 Node、pnpm、React、TypeScript、Vite和浏览器支持基线；
7. 完成第三方依赖及旧代码来源的许可证清单；
8. 为 WGS84/GCJ02/BD09 准备固定输入输出与允许误差；
9. 明确上海2000验证负责人、资料来源和通过门槛；
10. 确认 CGCS2000/天地图契约的验证计划；
11. 准备 Excel、CSV、JSON 的最小、正常和错误样本；
12. 取得三平台可用于开发验证的 Key及测试域名方案。

## 4.2 可以与Phase 1并行，但必须在对应实现前完成

- 三地图生命周期实机验证；
- Marker性能档位和目标设备；
- IndexedDB配额与升级策略细化；
- 算法版本编号和缓存键格式；
- 导入部分成功策略；
- API限额、隐私和凭据说明。

## 4.3 进入下一阶段的建议

结论为“**有条件可以进入项目初始化阶段**”：

- 可以开始工程骨架、依赖规则、路由壳、Domain接口和Design Token装配；
- 不应开始迁入上海2000正式算法、天地图坐标转换、地图性能阈值或生产凭据；
- Phase 1不得把未关闭的开放问题固化成不可逆数据模型。
